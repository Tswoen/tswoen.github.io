Agent 核心原理：RAG、CoT 与 ReAct

作者：汤文  日期：2025-08-12  阅读时长：约 11 分钟

这一篇整理了 Agent 最基础的几个概念：为什么需要 RAG、什么是 CoT、ReAct 循环怎么跑、AutoGen 的多智能体协作，以及一套完整的 Agent 设计方法论。

RAG 的优势

RAG（检索增强生成）之所以成为大模型应用的标准组件，主要有三点价值。

  • 让模型基于检索到的内容回答，有据可依，大幅减少幻觉，还能引用来源，明显缓解幻觉问题。
  • 大模型有训练截止时间，而 RAG 相对灵活，可以接入任何知识库，并且随时更新，不需要重新训练模型，非常适合知识快速变化的场景。
  • 上下文可控，回答更精准。直接问 LLM 时，长上下文容易丢失细节、跑题、冗余；RAG 只检索和问题相关的片段，精准喂给模型，减少无关信息干扰。

什么是 CoT

CoT（思维链）的核心思路是：不让模型直接输出问题的答案，而是通过提示词强制让模型经过一步步的思考推理，再引导出最终的答案。这会显著提高模型对问题解答的正确率，尤其是需要多步推理的场景。

ReAct 理解

ReAct 是 Reasoning 与 Acting 的结合，也就是推理与行动。它让 LLM 按照「思考 -> 行动 -> 观察」这个循环来推进任务：先使用 CoT 思维链思考当前该怎么做，然后系统解析模型输出的工具调用，并执行对应的工具，把工具返回的结果作为新的「观察」接收回来，再进入下一轮思考，直到 LLM 判断任务完成。

这个循环把「想」和「做」交织在一起，模型不再是盲猜答案，而是每一步都能拿到真实环境的反馈，因此对复杂任务的完成质量提升明显。

对 skills 的理解与平时的应用

Skills 可以理解为按需加载的能力包，把特定场景的流程、规范和模板沉淀成独立的文档，Agent 在需要时再读取正文，平时只在系统提示词中暴露元数据，从而避免污染上下文。

平时对 skills 的使用主要有两类：

  • 文献阅读 Skill：固定文献阅读的流程与输出结构，让每篇论文的拆解维度保持一致。
  • 论文润色 Skill：不覆盖原文本，而是在特殊符号中扩住修改后的内容，并给出修改原因，方便逐条确认后再决定是否采纳。

AutoGen 的理解

AutoGen 是微软的多智能体协作框架，通过定义不同角色的 Agent，比如规划、编码、评审，让它们自主对话、分工协作完成复杂任务。它可以自我纠错、多轮迭代，适合复杂任务生成这类多步骤场景。

选择它的原因：支持多 Agent 自由对话与群聊协作，是真正面向多角色协同的框架，与项目中的使用场景高度适配；而且 AutoGen 社区成熟，文档比较完善，学习成本低，用的人也更多。

Agent 流程：让你做某个 Agent，你怎么做

第一步是明确 Agent 要做什么任务，然后按复杂度选择架构。

  • 简单任务：使用 ReAct 架构，边想边做，循环推进即可。
  • 复杂长任务：使用 Plan-and-Execute，先整体规划步骤，再分步执行，每一步可以创建子 Agent 使用 ReAct 来完成子任务。
  • 输出有严格要求：在每一步最后引入 Self-Reflection，增加「生成 -> 评估 -> 改进」的闭环，判断当前的输出有没有问题、达不达标，不达标就重试或调整策略，直到符合要求为止。

架构确定后，为了让 Agent 系统长期稳定运行，还需要搭建一套 Agent 工程化 Harness 平台，把输入层、输出层和维护层都约束起来：Agent 的输入层负责上下文与工具装配，输出层负责格式与质量校验，维护层负责长期健康度，比如文档同步、规则清理和记忆整理。

Agent 幻觉问题

控制幻觉可以按层次来做防御。

  • 第一层：源头约束，强化提示词（系统 Prompt），把边界、负面清单和输出要求写清楚。
  • 第二层：RAG / 检索增强，事实锚定，Agent 推理时强制绑定参考来源，无依据的内容不输出。
  • 第三层：Self-Reflection 自省闭环，输出最终结果前加入自省校验，让模型自己检查是否有无依据的表述。
  • 如果是工具调用幻觉，则通过执行层校验来处理，比如参数强校验、返回值校验，禁止模型脑补补全。

Harness Engineering

在深入探讨 Harness Engineering 之前，必须首先理解它所处的演化脉络。参考链接：https://zhuanlan.zhihu.com/p/2021680667864363673

一、AI 工程的三次浪潮

  • 1. 提示词工程（Prompt Engineering）——「教 AI 如何对话」：该阶段的核心焦点是优化与 AI 的单次交互。工程师们通过精心设计的提示词，利用诸如 Few-shot、思维链（Chain-of-Thought）等技巧，试图引导模型在单次问答中给出更精准的输出。但对于处理复杂、多步骤任务的 Agent，单条指令的局限性暴露无遗。
  • 2. 上下文工程（Context Engineering）——「为 AI 提供正确的背景」：核心是管理提供给模型的信息，确保 Agent 在执行任务时拥有足够的背景知识，包括检索增强生成（RAG）、对话历史管理、工具输出整合等技术。它提升了 AI 在单次任务中的表现，但缺乏对其输出的主动控制和纠错机制，面对长期、复杂的任务时，Agent 依然会面临稳定性不足、行为失控等问题。
  • 3. 驾驭工程（Harness Engineering）——「设计 AI 工作的系统」：它代表了从「优化输入」到「优化环境」的根本性思维转变，将其提升到全生命周期控制系统设计的层面。它通过引入架构约束、反馈回路、熵管理等机制，为 AI Agent 构建了一个能够长期、稳定、高质量完成工作的「操作系统」或「脚手架」，将工程的重心完全转移到系统环境的设计上。

二、Harness 的三位一体

Harness Engineering 并非单一技术的名称，而是一个由三个核心支柱构成的系统工程框架：上下文工程、架构约束和熵管理。它们共同构成了一个完整的 Harness，缺一不可。

1. 上下文工程：这是 Harness 的「信息层」，也可以理解为 Agent 的输入端。其核心目标是确保 Agent 在正确的时间获得正确的信息，从而解决「知识」的问题。

  • 渐进式披露：让 Agent 可以根据需要，动态地加载相关信息，而非一次性塞给它们一本厚重的公司百科全书。
  • 动态可观测性：通过将日志、指标、追踪等可观测性数据暴露给 Agent，赋予 Agent「看见」其自身工作和系统运行时状态的能力，使其能够查询服务性能、验证自身操作结果，这是实现自我修正闭环的关键。
  • 工具定义即协议：使用 JSON Schema 等结构化格式，明确规定每个工具的名称、用途、参数、调用条件及相互关系。
  • 最小权限原则：为 Agent 提供完成任务所必需的最小工具集，是降低复杂性和减少错误的有效策略，因为更少的选择意味着更少的决策干扰和更少的出错机会。

2. 架构约束：这是 Harness 的「规则层」，对应 Agent 的输出端。其核心目标是确保 Agent 的产出严格遵守预定义的系统边界和质量要求，从而解决「行为」的问题。

  • 确定性护栏：对于那些可以被形式化规则清晰定义的约束（如代码风格、导入路径限制、API 调用规范），由确定性代码（如 Linter、CI 脚本、预处理钩子）执行硬性检查。例如，与其在提示词中说「请不要修改某某文件的代码」，不如编写一个自定义 Linter 规则，自动扫描并拦截任何违反此架构原则的代码提交。
  • 非确定性护栏：基于 LLM 的审计 Agent，用于检查那些更为复杂、隐性的语义规则，这些规则难以用形式化语法表达，比如「系统分层之间的依赖方向」、「关键业务逻辑的合规性」。由一个独立的 LLM Agent 来扮演「架构审查员」的角色，对主 Agent 的产出进行二次评估。

3. 熵管理：这是 Harness 的「维护层」，核心目标是确保整个 Harness 系统自身能够随着时间推移而持续保持健康，从而解决系统的「长期可持续性」问题，也就是 Agent 的长期稳定性。

  • Harness 的自愈（Harness Self-Healing）：熵在这里具体表现为 Harness 内部文档的腐化、约束规则的过时与矛盾。如果 Harness 自身变得混乱，Agent 的产出也将不可避免地混乱。因此，必须设计专门的「清理 Agent」或自动化流程，定期扫描整个系统，检测和修复诸如文档内容与代码库实际状态不符（文档漂移）、存在相互冲突的指令、工具定义发生变化但未更新协议等问题。

以上几个方面共同实现了 Harness 工程，用来保证 Agent 的长期稳定运行。

MCP 的意义

在 MCP 出现之前，不同的 AI 应用接入工具的方式不同，而且不同模型的 Function Calling 格式不完全一样，所以为 AI 应用接入新的工具时都需要额外写工具 schema 和对接逻辑。一旦工具要修改，需要为每个使用到该工具的 AI 应用都进行修改，而且这套代码和具体模型强绑定，换个模型就得重写，非常繁琐。

MCP 就是为「AI 接工具」这件事定了一套统一的协议标准。工具提供方按协议实现一个 Server，任何支持 MCP 的 AI 客户端就能直接接进来，一次实现到处复用。

MCP 由三层组成：

  • 角色层：定义了三个角色。MCP host 就是 AI 应用本身；MCP server 就是工具提供方编写的一个遵循了 MCP 协议的工具服务；MCP client 就是 AI 应用中用于和 MCP server 进行通信交互的模块。
  • 能力层：定义了 Server 能暴露三类东西。Tools 是可调用的工具，Resources 是只读数据（比如读取文档内容），Prompts 是预定义的提示词模板。
  • 协议层：规定消息格式统一用 JSON-RPC 2.0，传输方式支持 stdio（本地子进程通信）和 Streamable HTTP（远程 HTTP 连接）两种。

MCP 统一了 AI 应用与工具的对接方式，使得所有支持 MCP 的客户端 AI 应用都可以无缝连接到 MCP 服务提供的工具。并且也统一了工具的 schema，这样 MCP client 便可以将这个统一的工具 schema 转换成不同模型的 Function Calling 格式，从而对不同厂商的模型进行适配。

如何设计一个比较好的 Prompt

基础做法是通过代码模版引擎，把它们做成一个个独立模块拼接起来，并采用静态前缀和动态后缀的设计，增加 Prompt Cache 的缓存命中率。

在这个基础上可以分三层来组织：

  • System Prompt（最静态，最优先缓存）：角色定义、整体目标、能力边界与负面清单（能做什么，不能做什么）、思考流程（CoT 规则）、输出格式要求（JSON Schema 等）。
  • 工具定义 + Few-shot 示例（半静态）：工具描述和 JSON Schema（尽量不要在会话中动态增删工具，否则会破坏缓存），正反 Few-shot 示例。
  • 动态上下文（放在最后）：当前用户查询、最近的对话历史（或总结后的历史）、实时检索到的 RAG 内容、当前工具执行结果（Observation）。

这样分层之后，越静态的内容越靠前，缓存命中率越高，越动态的内容越靠后，既保证了效果又控制了成本。
